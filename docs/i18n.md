# i18n guide: adding strings and locales

ChainSettle uses [`next-intl`](https://next-intl-docs.vercel.app/) (v3) for all user-facing text. Every string a user can read, including button labels, headings, empty states, errors, `aria-label`s and placeholders, should come from a message file, not be written into the component.

## How it is wired

| File | Role |
|------|------|
| `src/i18n/config.ts` | The list of supported `locales`, `defaultLocale` (`en`), `localeLabels` (names shown to users), `LOCALE_COOKIE` (`NEXT_LOCALE`) and the `isLocale()` type guard. |
| `src/i18n/messages/<locale>.json` | One message file per locale. `en.json` is the source of truth; every other locale must have the same keys. |
| `src/i18n.ts` | Request config for **server components**. It reads the `NEXT_LOCALE` cookie, falls back to `defaultLocale` if the value is not in `locales`, and loads `messages/<locale>.json`. |
| `next.config.js` | Registers that request config with `createNextIntlPlugin('./src/i18n.ts')`. |
| `src/app/providers.tsx` | Wraps the app in `NextIntlClientProvider`, which supplies messages to **client components**. It currently passes `locale="en"` and `en.json`. |

Routes are not prefixed with a locale (there is no `/fr/...`). The locale for server rendering comes from the `NEXT_LOCALE` cookie.

## Adding a string

### 1. Add the key to `en.json`

Find the namespace that matches the feature (the top-level keys are `navigation`, `dashboard`, `events`, `settings`, `shipments`, `milestones`, `arbiter`, `notifications`, `errors`, `contractErrors`, `proofDocument`, `notFound`, `session`). Add your key there, or create a new namespace for a new feature area.

```json
{
  "shipments": {
    "title": "Shipments",
    "exportCsv": "Export CSV",
    "exportedCount": "{count, plural, =1 {# shipment exported} other {# shipments exported}}"
  }
}
```

Messages use ICU syntax:

- Variables: `"network": "Stellar {network}"`, then `t('network', { network: 'testnet' })`.
- Plurals: `"{count, plural, =1 {# milestone} other {# milestones}}"`, then `t('milestoneCount', { count: 3 })`.

If other locale files exist, add the same key to each of them (use the English text until a translation is available, so nothing renders as a missing key).

### 2a. Use it in a client component

Client components (files starting with `'use client'`) use the `useTranslations` hook. Pass the namespace once and use short keys, with dots for nested keys:

```tsx
'use client';

import { useTranslations } from 'next-intl';

export function ExportButton({ count }: { count: number }) {
  const t = useTranslations('shipments');

  return (
    <button className="btn-secondary" aria-label={t('exportCsv')}>
      {t('exportCsv')} · {t('exportedCount', { count })}
    </button>
  );
}
```

Examples in the codebase: `src/components/layout/Sidebar.tsx` (`useTranslations('navigation')`), `src/app/dashboard/shipments/page.tsx` (`t('tabs.all')`), `src/components/templates/TemplateManager.tsx` (nested namespace `useTranslations('settings.templates')`).

### 2b. Use it in a server component

Server components (no `'use client'`, may be `async`) use `getTranslations` from `next-intl/server`:

```tsx
import { getTranslations } from 'next-intl/server';

export default async function NotFound() {
  const t = await getTranslations('notFound');

  return <h1>{t('title')}</h1>;
}
```

See `src/app/not-found.tsx`. For page metadata, call `getTranslations` inside `generateMetadata`:

```tsx
import { getTranslations } from 'next-intl/server';

export async function generateMetadata() {
  const t = await getTranslations('shipments');
  return { title: t('title') };
}
```

A non-async server component that is rendered inside the client provider (for example `src/app/dashboard/shipments/[id]/not-found.tsx`) can also use `useTranslations`.

### 3. Strings outside components

Plain functions in `src/lib` cannot call hooks. Return a stable code or key from the function and translate it in the component. `TransactionError` does this for contract errors: `parseContractError` returns a `code`, and the component renders `t(\`codes.${error.code}\`)` from the `contractErrors` namespace.

## Key naming conventions

- **Namespace = feature or page.** The top-level key matches the area of the app (`shipments`, `milestones`, `settings`). Use a nested object for a sub-area (`settings.templates`, `dashboard.tabs`, `dashboard.empty`).
- **camelCase keys**, as in the existing file: `newShipment`, `searchPlaceholder`, `walletConnectionFailed`. Do not use snake_case or spaces.
- **Name keys by meaning, not by text.** `confirmMilestone`, not `confirm` or `clickHereToConfirm`, so the key still fits if the English wording changes.
- **Common suffixes:**

  | Suffix | Use | Example |
  |--------|-----|---------|
  | `Title` / `title` | Headings, dialog titles | `session.expiringTitle` |
  | `Description` | Supporting text under a title | `errors.notFoundDescription` |
  | `Label` | `aria-label`s and form labels | `navigation.notificationsLabel` |
  | `Placeholder` | Input placeholders | `dashboard.searchPlaceholder` |
  | `Count` | Pluralized counts (ICU `plural`) | `events.eventCount` |
  | `empty` object | Empty-state `title` / `description` | `dashboard.empty.title` |

- **Do not reuse a key across features** just because the English text matches today. Duplicate it under each namespace; translations may differ by context.
- **Do not rename or delete keys** without updating every `t(...)` call and every locale file.

## Adding a new locale

The example below adds German (`de`). Replace the code and label with your locale.

1. **Create the message file.** Copy `src/i18n/messages/en.json` to `src/i18n/messages/de.json` and translate the values. Keep every key and every ICU placeholder (`{count}`, `{name}`, `#`) unchanged.

2. **Register the locale** in `src/i18n/config.ts`:

   ```ts
   export const locales = ['en', 'fr', 'de'] as const;

   export const localeLabels: Record<Locale, string> = {
     en: 'English',
     fr: 'Français',
     de: 'Deutsch',
   };
   ```

   `localeLabels` is typed as `Record<Locale, string>`, so TypeScript will fail until the new label is added. Server components now pick up `de.json` automatically through `src/i18n.ts` when the `NEXT_LOCALE` cookie is `de`.

3. **Load the messages for client components** in `src/app/providers.tsx`. The provider currently hard-codes English; give it the locale and pick the matching bundle:

   ```tsx
   import { NextIntlClientProvider } from 'next-intl';
   import type { Locale } from '@/i18n/config';
   import en from '@/i18n/messages/en.json';
   import fr from '@/i18n/messages/fr.json';
   import de from '@/i18n/messages/de.json';

   const messages = { en, fr, de } satisfies Record<Locale, typeof en>;

   export function Providers({ children, locale }: { children: React.ReactNode; locale: Locale }) {
     // ...
     return (
       <NextIntlClientProvider locale={locale} messages={messages[locale]}>
         {children}
       </NextIntlClientProvider>
     );
   }
   ```

   Then pass the locale from `src/app/layout.tsx`, using the same source as the server config:

   ```tsx
   import { getLocale } from 'next-intl/server';

   export default async function RootLayout({ children }: { children: React.ReactNode }) {
     const locale = (await getLocale()) as Locale;
     return (
       <html lang={locale} suppressHydrationWarning>
         <body>
           {/* keep the existing skip link here */}
           <Providers locale={locale}>{children}</Providers>
         </body>
       </html>
     );
   }
   ```

   Every bundle listed in `messages` must exist, so each locale in `locales` needs its JSON file. (At the time of writing `fr` is listed in `config.ts` but `fr.json` has not been added yet; add it before wiring the provider this way.)

4. **Let users switch.** A language selector sets the cookie and refreshes the page so server components re-render:

   ```tsx
   'use client';

   import { useRouter } from 'next/navigation';
   import { locales, localeLabels, LOCALE_COOKIE, type Locale } from '@/i18n/config';

   export function LocaleSelect({ value }: { value: Locale }) {
     const router = useRouter();
     return (
       <select
         className="input"
         value={value}
         onChange={(e) => {
           document.cookie = `${LOCALE_COOKIE}=${e.target.value}; path=/; max-age=31536000; samesite=lax`;
           router.refresh();
         }}
       >
         {locales.map((l) => (
           <option key={l} value={l}>{localeLabels[l]}</option>
         ))}
       </select>
     );
   }
   ```

5. **Check it** before opening a PR:
   - `npx tsc --noEmit` passes (catches a missing `localeLabels` entry or a missing JSON import).
   - The new JSON file has exactly the same keys as `en.json`. A quick check:

     ```bash
     node -e "const f=(o,p='')=>Object.entries(o).flatMap(([k,v])=>typeof v==='object'?f(v,p+k+'.'):[p+k]);const a=new Set(f(require('./src/i18n/messages/en.json'))),b=new Set(f(require('./src/i18n/messages/de.json')));console.log('missing:',[...a].filter(k=>!b.has(k)));console.log('extra:',[...b].filter(k=>!a.has(k)))"
     ```

   - In the browser, set the cookie (`document.cookie = 'NEXT_LOCALE=de; path=/'`), reload, and check a server-rendered page (e.g. a 404 page) and a client page (the shipments list, the sidebar). Both should show the new language, and `<html lang>` should match.
   - Clear the cookie and confirm the app falls back to English.

## Checklist for a PR that adds UI text

- [ ] No hard-coded user-facing strings, including `aria-label`, `title`, `placeholder` and `alt`.
- [ ] New keys are in `en.json` under the right namespace, in camelCase.
- [ ] The same keys exist in every other locale file.
- [ ] Counts use ICU `plural`; variables use `{name}` placeholders rather than string concatenation.
- [ ] Client components use `useTranslations`; async server components use `getTranslations`.

See also [`src/i18n/I18N.md`](../src/i18n/I18N.md) for more `next-intl` examples (formatting numbers and dates).
